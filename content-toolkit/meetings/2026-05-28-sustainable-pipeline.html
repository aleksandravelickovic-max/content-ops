    02 / 15 Mental model

    One sentence to reset on.

    You don't need a separate Roto-Rooter-style app. The same pattern that produces 1,000+ RR pages runs natively inside Claude Code: one session, one parallel command, N pieces fan out as sub-agents at the same time. The repo already has it. The agentic pivot, in plain English

    What this is NOT

    • A web app the team needs to log into.
    • A black box that calls OpenRouter behind the scenes.
    • A separate codebase from what you're already using.
    • An AI that replaces the writers' judgment.

    What this IS

    • A toolkit of Claude Code commands the team runs.
    • A repo where rules + materials + voice live (and get edited).
    • A parallel fan-out pattern that scales without burning sessions.
    • A feedback loop: every editorial fix becomes a permanent rule.

    04 / 15 Diagnosis

    The speed complaint, diagnosed.

    Aleksandra surfaced what looked like one problem. Underneath it were three.

    We've been utilizing the CC setup but the speed is the issue. Yes, we've been running into usage blocks A LOT. Aleksandra Velickovic, in DMs — the trigger for today's work

    Three real gaps, not one

    1

    No parallel orchestrator

    The team was running /run-piece serially — one piece per Claude Code session. That's the most expensive way to use the plan: every piece pays a fresh session token budget.

    2

    No documented improvement loop

    When a gate failed, the instinct was to re-prompt or hand-edit. That keeps the pipeline producing the same mistake on the next batch — the system never gets smarter.

    3

    Material configs had drifted

    Six material rule errors vs. Emanuel's Materials Reference Guide v3 (live-site truth). material-guard would have let factual mistakes pass on terrazzo, ceramics, limestone, cantera, marble, roman-mosaics.

    All three are fixed as of today (17 commits, Wave 5). The rest of this deck is how the team now operates around the fixes — the sustainable, self-improving process.
    05 / 15 Framework

    Three pillars of a sustainable pipeline.

    These are not features. They're practices. If we keep doing all three, the system compounds. If we drop any one, we slide back to manual writing with extra steps.

    PILLAR 01

    Parallel execution

    Stop running pieces one at a time. Fan out N pieces in one session as concurrent sub-agents. Same plan, fraction of the wall time.

    Tool: /parallel-pieces

    PILLAR 02

    Self-improvement loop

    Every gate failure or editorial rejection becomes a permanent rule. We fix the source (prompt, config, knowledge), not the symptom.

    Tool: IMPROVEMENT-LOOP.md

    PILLAR 03

    Living knowledge base

    The repo is the source of truth, not the model. Style, voice, compliance, material rules live in files. Git is the system's memory.

    Tool: clients/{name}/

    Why all three matter together

    Parallel without improvement = fast bad content. Improvement without parallel = slow good content. Both without a living knowledge base = a system that forgets between sessions. Only with all three running do we get a pipeline that gets both faster and better over time.

    06 / 15 Pillar 01

    Parallel execution.

    The session is the bottleneck, not the work. The Max plan can comfortably orchestrate 20-50 pieces fanned out concurrently — same pattern Lucas runs on Roto-Rooter for 1,000+ pages.

    ✗ Serial · what we were doing

    10 pieces × 12-15 min × 1 fresh session each

    10 sessions · ~2-3 hours wall time
    Rate limits hit constantly

    ✓ Parallel · what we do now

    All 10 pieces in one session, concurrent sub-agents

    1 session · ~25-35 min wall time
    No rate-limit pressure

    How to invoke it

    # 12 SKUs in the Cotto colorway, in parallel:
/parallel-pieces zia-tile product cotto 12

# Explicit list (re-running specific failed pieces):
/parallel-pieces zia-tile product cotto "red-clay-8x8,adobe-4x4"

# Derived from an approved collection:
/parallel-pieces zia-tile product zellige 8 --from-collection zellige-collection

    When to use what

    SituationUse
    Producing 1 piece, careful single-shot/run-piece
    Promoting one approved v3 draft/promote-v3
    Multiplying SKUs off an approved collection/sku-multiplier now parallel
    Net-new batch of N pieces/parallel-pieces use this
    Pure QA scan across an existing backlog/batch-review
    07 / 15 Pillar 02

    The self-improvement loop.

    This is the most important practice. Without it, the pipeline is just a fancy bulk-writer. With it, the system gets measurably smarter every batch.

    batch run → some pieces fail → diagnose where → fix the SOURCE → re-run only the failed → commit the fix

    The one rule that makes this work

    The system's memory is git, not the model. When you find a recurring mistake, fix it in the repo — not by re-prompting harder. Otherwise we re-discover the same issue every batch.

    Three places to fix the source

    The prompt

    A drafter keeps producing weak leads on a material → update draft-product-page.md with an explicit lead-quality rubric. Commit.

    The config

    Material rule disagrees with Emanuel's v3 reference → reconcile materials/{material}.md. Commit, citing the source.

    The knowledge

    A claim has no source in raw/ → add a fact file with the citation, OR remove the claim. Never invent.

    The reference example

    The 2026-05-25 reconciliation is the canonical case. Ten atomic commits, one per material, each citing the authoritative reference. Six rule flips on terrazzo, ceramics, limestone, cantera, marble, roman-mosaics. material-guard now blocks errors that would have shipped two weeks ago.

    09 / 15 How to run a day

    The daily workflow, step by step.

    This is what running a batch looks like end-to-end — from "we need 20 product pages this week" to "20 drafts in review."

    1

    Pick the batch

    Decide what you're producing this session: client + content type + material + count. Keep batches scoped to one material at a time — the gates' reads amortize within a material.

    e.g. "12 Cotto product SKUs" or "8 zellige blog posts"
    2

    Run /parallel-pieces

    One session, N sub-agents. Each one drafts a piece and runs the four mechanical gates inline. The orchestrator returns the matrix.

    /parallel-pieces zia-tile product cotto 12
    3

    Read the matrix

    The orchestrator returns a per-piece grid: which gates passed, which failed, and where files landed. Don't open each draft yet — triage from the matrix.

    4

    Score the clean pieces

    For the pieces that passed mechanical gates, run voice-judge + koray-judge as a second parallel batch. Anything ≥ 80/80 goes to editorial review.

    5

    Triage the failures — ask "where?"

    For every failed piece, ask: did the prompt produce this mistake, or did the config let it through? Don't re-prompt. Open the source. (See slide 10's decision tree.)

    6

    Fix the source — commit

    Edit the prompt, config, or knowledge file. One atomic commit per fix, message names the dimension. The git log is the audit trail.

    fix(zia): cantera freeze/thaw not_suitable — per Materials Reference Guide v3
    7

    Re-run ONLY the failed pieces

    The parallel orchestrator accepts an explicit piece list. Use it. Don't re-run the whole batch — that's a waste of plan budget and review effort.

    /parallel-pieces zia-tile product cotto "red-clay-8x8,oscura-2x6"
    10 / 15 Triage

    When a gate fails: where do you look?

    Six gates, six decision rules. Memorize these — this is what turns a failed batch into a system upgrade instead of a re-prompt session.

    GateWhat it caughtWhere to fix
    material-guard Wrong pool/spa, freeze/thaw, sealing, or variation rule on a material. Open materials/{material}.md. Check against materials-reference.md. If config disagrees with reference → config wins gets flipped. If draft disagrees with config → fix the draft (or the drafter prompt).
    terminology-lint Banned term used, required term missing, second person in body. If STYLE-SYSTEM §3.2 already banned it → fix the draft. If it's a judgment call → tighten agents/terminology-lint.md with the contextual rule.
    person-consistency Second person in body, or first/third person switching mid-piece. Almost always a draft fix. Exception: if a new content type legitimately uses second person, update page-templates/{type}.md.
    contact-line-check Required contact line missing or wrong wording. Fix the draft. If the contact line itself changed, update contact-block.md once.
    voice-judge < 80 Reads too marketer-y, weak lead, weak closer, generic register. If one dimension tanks across many pieces → update the drafter prompt with concrete examples + emphasis. If only one piece tanks → fix that piece manually.
    koray-judge < 80 SEO structure, entity coverage, internal-link depth, schema readiness. Dimension-by-dimension review. Most common pattern: weak internal-link depth → update drafter to always link the Installation Guide + sibling product.
    claims-grounding A claim has no source in raw/. True but missing? → add a raw/knowledge/facts/{slug}.md with the citation. Unverifiable? → remove from draft. Never invent.
    The pattern across every row: the draft is never authoritative. It's always either the prompt, the config, or the knowledge base — one of which needs the permanent fix.
    11 / 15 Rhythm

    Cadence: how often we do what.

    Sustainability is a rhythm, not a one-time setup. Three nested loops — per batch, weekly, per new material.

    PER BATCH

    10-15 minutes after the matrix

    Find the most common failure dimension in this batch. Fix it in the source. Commit. That's the daily improvement-loop pass.

    • Read the matrix
    • Cluster failures by dimension
    • Pick the top one
    • Fix + commit
    • Re-run only failed pieces
    WEEKLY

    Friday: re-read STYLE-SYSTEM

    Compare it against everything Jamie / Aleksandra corrected this week. Anything that was an editorial fix but isn't in STYLE-SYSTEM yet is about to be missed again.

    • Scan the week's editorial edits
    • Identify repeated patterns
    • Promote them to rules
    • Update STYLE-SYSTEM + commit
    PER NEW MATERIAL

    Read first, produce second

    Before producing the first batch on a new material, read materials-reference.md for that material end-to-end. The Quick Reference matrix is the cheapest place to find the next rule flip.

    • Read reference doc end-to-end
    • Cross-check against the config
    • Flip any disagreements
    • Commit before first batch

    The compounding effect

    The first few batches surface 80% of the recurring rules. By batch 5-6 on a given material, the gates catch failures so well that editorial review starts from a clean draft. That's when the team flips from "writing" to "editing + QA," which was the whole point of this build.

    12 / 15 Avoid

    Anti-patterns — what to NOT do.

    These are the ways the system silently slides back into manual work. If you catch any of these happening, surface it — that's the real problem to solve.

    ✗
    Anti-pattern
    Re-prompting until the gate passes
    Do instead
    If a gate keeps failing on similar pieces, the prompt or config has the bug. Fix the source. Commit. Re-run.
    ✗
    Anti-pattern
    Loosening a gate to make a draft pass
    Do instead
    A wrong pool/spa rule is a factual error. Loosening material-guard ships that error to clients. Fix the draft.
    ✗
    Anti-pattern
    Editing one piece per session indefinitely
    Do instead
    That's not the pipeline — that's manual writing with extra steps. If the system isn't producing at scale, find the bottleneck (prompt, config, or knowledge gap) and fix that.
    ✗
    Anti-pattern
    Treating Aleksandra's edit as a one-off
    Do instead
    When she rewrites the same kind of sentence twice, that's a rule. Encode it in STYLE-SYSTEM or the relevant agent prompt.
    ✗
    Anti-pattern
    Forking prompts into v2 / v3 folders to "save the old version"
    Do instead
    Edit in place. Git history is the version control. Don't fork unless you actually need to run two versions side-by-side.
    ✗
    Anti-pattern
    Running /run-piece in a loop for a 20-piece batch
    Do instead
    Use /parallel-pieces. That's literally why it exists. One session, N sub-agents.

    The per-client onboarding template

    To bring a new client into the toolkit, the per-client checklist is identical — just substitute the content:

    1

    Write clients/{name}/STYLE-SYSTEM.md

    Voice, register, structure rules, banned and required phrasing. Source = the CSM's brand brief and the client's existing best content.

    2

    Write COMPLIANCE.yml

    Fail-closed flags specific to this client's regulated context: medical, financial, peptide, gaming, federal, etc. This is the most important file for compliance-heavy clients.

    3

    Write contact-block.md + page-templates/

    What every page must include (contact line, CTAs) and the spine of each content type. Adapt from Zia's templates — same structure, different content.

    4

    Add one material/category config per offering

    For tile clients, materials. For aesthetics clients, procedures. For software clients, product lines. Same schema — the gate logic ports unchanged.

    5

    Run one verification piece

    Use /run-piece on a single seed page. Confirm all gates pass. Then graduate to /parallel-pieces for the first real batch.
