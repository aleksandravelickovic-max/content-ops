07 / 24 · Diagnosis

Three real gaps, not one.

01

No parallel orchestrator

The team was running /run-piece serially — one piece per Claude Code session. The most expensive way to use the plan: every piece pays a fresh session token budget.

02

No documented improvement loop

When a gate failed, the instinct was to re-prompt or hand-edit. That keeps the pipeline producing the same mistake on the next batch — the system never gets smarter.

03

Material configs had drifted

Six rule errors vs. Emanuel's Materials Reference Guide v3. material-guard would have let factual mistakes pass on terrazzo, ceramics, limestone, cantera, marble, roman-mosaics.

All three were fixed today — 17 commits, Wave 5. The rest of this deck is the sustainable process built around the fixes.

09 / 24 · Pillar 01 — Parallel execution

The session is the bottleneck, not the work.

The Max plan can comfortably orchestrate 20-50 pieces fanned out concurrently — same pattern Lucas runs on Roto-Rooter for 1,000+ pages.

✗ Serial · what we were doing
10 pieces × 12-15 min × 1 fresh session each
~2-3 hours wall time. Rate limits hit constantly.
✓ Parallel · what we do now
All 10 pieces in one session, concurrent sub-agents
~25-35 min wall time. No rate-limit pressure.

11 / 24 · Pillar 02 — Self-improvement loop

The loop that makes the system get smarter.

Without this practice, the pipeline is just a fancy bulk-writer. With it, the system gets measurably smarter every batch.

batch run → some pieces fail → diagnose where → fix the SOURCE → re-run only failed → commit the fix
The one rule

The system's memory is git, not the model. When you find a recurring mistake, fix it in the repo — not by re-prompting harder.

12 / 24 · Pillar 02 — Self-improvement loop

Three places to fix the source.

The draft is never authoritative. Failure always traces back to one of these three places.

The prompt

Drafter / agent file

A drafter keeps producing weak leads on a material → update draft-product-page.md with an explicit lead-quality rubric. Commit.

The config

Material / compliance

Material rule disagrees with Emanuel's v3 reference → reconcile materials/{material}.md. Commit, citing the source.

The knowledge

raw/ research files

A claim has no source in raw/ → add a fact file with the citation, OR remove the claim. Never invent.

The May 25 reconciliation is the canonical case: 10 atomic commits, one per material, each citing the authoritative reference. Six rule flips. material-guard now blocks errors that would have shipped two weeks ago.

13 / 24 · Pillar 03 — Living knowledge base

The repo is the source of truth.

Every rule, every voice constraint, every material fact lives in a file. The model never holds the system's memory — the repo does.

├── page-templates/          # spine per content type
│   └── collection.md · product.md · blog.md

Onboarding a new client = replicating this shape. Same schema, different content. The pipeline picks it up automatically.

15 / 24 · Daily workflow — Setup phase

A day in the pipeline. Setup.

From "we need 20 product pages this week" to a triable matrix — four steps.

01

Pick the batch

Client + content type + material + count. Scope batches to one material — gate reads amortize within a material.

02

Run /parallel-pieces

One session, N sub-agents. Each one drafts a piece and runs the four mechanical gates inline. The orchestrator returns the matrix.

/parallel-pieces zia-tile product cotto 12
03

Read the matrix

Per-piece grid: which gates passed, which failed, where files landed. Don't open each draft yet — triage from the matrix.

04

Score the clean pieces

For pieces that passed mechanical gates, run voice-judge + koray-judge as a second parallel batch. ≥ 80/80 → editorial review.

16 / 24 · Daily workflow — Improvement phase

A day in the pipeline. Improvement.

The three steps that turn a failed batch into a system upgrade.

05

Triage failures — ask "where?"

For every failed piece, ask: did the prompt produce this, or did the config let it through? Don't re-prompt. Open the source. (Decision tree on the next two slides.)

06

Fix the source — commit

Edit the prompt, config, or knowledge file. One atomic commit per fix, message names the dimension. The git log is the audit trail.

fix(zia): cantera freeze/thaw not_suitable — per Materials Reference v3
07

Re-run ONLY the failed pieces

The orchestrator accepts an explicit list. Use it. Don't re-run the whole batch — that's wasted plan budget and review effort.

/parallel-pieces zia-tile product cotto "red-clay-8x8,oscura-2x6"
17 / 24 · Triage — Mechanical gates

When a mechanical gate fails.

Four cheap Haiku gates. They catch factual errors before review starts.

GateWhat it caughtWhere to fix
material-guard Wrong pool/spa, freeze/thaw, sealing, variation rule. Open materials/{material}.md. Cross-check vs materials-reference.md. Config disagrees with reference → flip the config. Draft disagrees with config → fix the draft.
terminology-lint Banned term used, required term missing, second person in body. STYLE-SYSTEM §3.2 already bans it → fix draft. Judgment call → tighten agents/terminology-lint.md.
person-consistency Second person in body, or 1st/3rd switch mid-piece. Almost always a draft fix. Exception: if new content type legitimately uses 2nd person → update page-templates/{type}.md.
contact-line-check Required contact line missing or wrong wording. Fix the draft. If the line itself changed → update contact-block.md once.
18 / 24 · Triage — Scored judges

When a scored judge fails.

Three Sonnet judges. Sub-80 → look at dimension breakdown, then update the prompt or knowledge.

GateWhat it caughtWhere to fix
voice-judge < 80 Reads marketer-y, weak lead, weak closer, generic register. One dimension tanks across many pieces → update drafter prompt with concrete examples. Only one piece tanks → fix that piece manually.
koray-judge < 80 SEO structure, entity coverage, internal-link depth, schema. Dimension-by-dimension. Most common: weak internal-link depth → update drafter to always link Installation Guide + sibling product.
claims-grounding A claim has no source in raw/. True but missing? → add raw/knowledge/facts/{slug}.md. Unverifiable? → remove. Never invent.

Pattern across every row: the draft is never authoritative. It's always the prompt, the config, or the knowledge that needs the permanent fix.

19 / 24 · Rhythm

Three nested loops. A rhythm.

Sustainability is cadence, not setup.

Per batch

10-15 min after the matrix

Find the most common failure dimension. Fix it in the source. Commit. That's the daily improvement-loop pass.

Weekly

Friday: re-read STYLE-SYSTEM

Compare against the week's editorial edits. Anything Jamie / Aleksandra corrected that isn't in STYLE-SYSTEM yet is about to be missed again.

Per new material

Read first, produce second

Read materials-reference.md end-to-end before the first batch. The Quick Reference matrix is the cheapest place to find the next rule flip.

The compounding effect: first few batches surface 80% of recurring rules. By batch 5-6, the gates catch failures so well that editorial review starts from a clean draft. That's when the team flips from writing to editing + QA — the whole point of this build.

20 / 24 · Avoid — Part 1

Anti-patterns. What not to do.

The ways the system silently slides back into manual work. Catch any of these → surface it. That's the real problem to solve.

✗
Anti-pattern
Re-prompting until the gate passes
Do instead
If a gate keeps failing on similar pieces, the prompt or config has the bug. Fix the source. Commit. Re-run.
✗
Anti-pattern
Loosening a gate to make a draft pass
Do instead
A wrong pool/spa rule is a factual error. Loosening material-guard ships that error to clients. Fix the draft.
✗
Anti-pattern
Editing one piece per session indefinitely
Do instead
That's not the pipeline — that's manual writing with extra steps. Find the bottleneck (prompt, config, knowledge) and fix that.
21 / 24 · Avoid — Part 2

Anti-patterns, continued.

✗
Anti-pattern
Treating Aleksandra's edit as a one-off
Do instead
When she rewrites the same kind of sentence twice, that's a rule. Encode it in STYLE-SYSTEM or the relevant agent prompt.
✗
Anti-pattern
Forking prompts into v2 / v3 folders to "save the old version"
Do instead
Edit in place. Git history is the version control. Don't fork unless you actually need to run two versions side-by-side.
✗
Anti-pattern
Running /run-piece in a loop for a 20-piece batch
Do instead
Use /parallel-pieces. That's literally why it exists. One session, N sub-agents.

23 / 24 · Forward — Per-client onboarding

The onboarding template, five steps.

Identical checklist for every new client. Substitute the content; the schema and the pipeline stay the same.

01

Write clients/{name}/STYLE-SYSTEM.md

Voice, register, structure rules, banned and required phrasing. Source = CSM's brand brief + the client's existing best content.

02

Write COMPLIANCE.yml

Fail-closed flags for this client's regulated context: medical, financial, peptide, gaming, federal. Most important file for compliance-heavy clients.

03

Write contact-block.md + page-templates/

Required contact line + spine of each content type. Adapt from Zia's templates — same structure, different content.

04

One config per offering category

Tile = materials. Aesthetics = procedures. Software = product lines. Same schema; gate logic ports unchanged.

05

Verification piece, then go parallel

Run one /run-piece on a seed page. Confirm all gates pass. Then graduate to /parallel-pieces for the first real batch.
